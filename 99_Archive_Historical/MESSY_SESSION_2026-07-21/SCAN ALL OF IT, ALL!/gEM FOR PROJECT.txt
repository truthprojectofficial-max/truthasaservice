To scale this infrastructure, the system must navigate several storage bottlenecks and cloud synchronization challenges. In its current state, the system relies on facts_registry.json to store audit trails. This file is loaded entirely into the memory stack upon application startup. While this design is straightforward, it presents a significant scaling bottleneck. As the Merkle ledger expands, the overhead of parsing and rewriting the entire JSON file blocks the single-threaded event loop, leading to transaction timeouts.   

To resolve this limitation, the system roadmap mandates migrating to a local, binary SQLite database (utilizing libraries such as better-sqlite3). This transition must be executed carefully to preserve the deterministic hashing mechanics of the Merkle ledger while moving from resource-heavy memory scans to efficient indexed reads.   

For cloud-based deployments where stateless containers (such as Azure App Service) are recycled regularly, local file operations and in-memory configurations risk data loss. To prevent database state loss, the architecture incorporates an Azure Files Storage Share named validation-vault-share. Configured within the South Australia geographic region (australiaeast), this storage share acts as a persistent, remote ground-truth store. By hosting the active SQLite database on this share, the system ensures that its structural evidence remains legally defensible and compliant with anti-spoliation directives.
